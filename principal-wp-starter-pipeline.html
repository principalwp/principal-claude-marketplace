How the Principal WP Starter Pipeline works

A tour of how the free starter takes one change to a WordPress plugin, theme, or mu-plugin from a plain request to a reviewed, tested pull request: the steps, the agents doing the work, and the three gates where a human signs off. It runs from the component's own repo.

What it is

The Principal WP Starter Pipeline takes one change to a WordPress plugin, theme, or mu-plugin from a plain request to a finished pull request. You give it a task in plain English; a formal ticket is optional, and a bare request is enough. It works through Requirements, Research, Spec, Code, and Review, stopping at three gates for you to sign off before any code is written.

It is a teaching starter, not a service. It shows how the work is done; it does not do the work for you. There is no orchestrator to stand up and no CI. Instead of one model doing everything in one pass, it runs focused agents in a fixed order, each with only the context it needs and every decision written to a file, so a person can read any decision later and a stopped run picks up from those files.

The shape of a run

A run walks the same order every time: Preflight, then Requirements, Research, and Spec (each ending at a gate), then Code, the four-reviewer fix loop, a certification, and the Compounding closeout. Nothing runs unattended. You drive every re-invocation, answer every gate, and run the final git push and gh pr create yourself. Underneath, a goal check surfaces a question if the task turns out to be already met, met more simply, or changed, rather than building against a goal it has just learned is wrong.

Everything is written to files under .principal-wp-starter-pipeline/<run-id>/ as it goes, and state.json is the resume authority. A run can stop at a gate, crash, or move to another machine, and the next invocation picks up exactly where it left off. The Steps tab is the whole sequence; State & files is where it all lives.

Install and run

A user-level skill install, then a one-time per-project setup. There is nothing to host.

1 · Install the skill and its agents once

cp -r .claude/skills/principal-wp-starter-pipeline ~/.claude/skills/
cp .claude/agents/principal-wp-starter-pipeline-*.md ~/.claude/agents/

2 · Run setup once per project

node ~/.claude/skills/principal-wp-starter-pipeline/setup.mjs

Setup fetches the WordPress Agent Skills, scaffolds the end-to-end test stack under tests/e2e/, and offers to install the language servers and dev tools. Commit that scaffold before your first run, so the clean-worktree check does not trip on it.

3 · Run it on a task

/principal-wp-starter-pipeline "<task text or path>"

Run this from the component's repo root. The argument is a task description or a bare request; if it is a path to a file, that file is read as the task text. The run closes with copy-pasteable git push and gh pr create commands, which you run yourself.

The setup gate is a hard halt. Every build run starts by checking that setup ran (setup.mjs --check). If it hasn't, the run stops and prints the command. No flag or mode skips it: the test stack has to be there before any agent is spawned.

The whole procedure lives in one orchestrator skill, SKILL.md.

Every step, in order, and where it can stop

A run always walks the same stages in order, and never skips one or runs two at once. The whole procedure lives in one orchestrator, SKILL.md, re-read rather than run from memory. Lands at is the state.json phase recorded once a step returns STATUS: ok; Gate (■) marks where the run stops for you.

Preflight runs before any phase: the setup-gate check (a hard halt), create the scratch dir, detect git and enforce a clean-worktree gate on a fresh run, add the scratch dir to .gitignore, an optional language-server check, and find the plugins, themes, and mu-plugins to mount. It records state.json with the components and the resume phase. A repo with no git edits files in place and skips the branch and PR steps.

How a gate asks, and how a run stops. At each ■ gate an agent writes its questions to a file; the orchestrator prints that file's path, asks the questions through an AskUserQuestion dialog, and records your answers there. Every in-scope and out-of-scope call is yours. A dismissed dialog leaves the gate unanswered, and no flag or mode skips the three gates. Separately, a STATUS: blocked from any build agent stops the run until you fix the named input and re-invoke; the three closeout steps are the only agents that finish even when blocked.

The twelve agents

The orchestrator (the skill) spawns these and does no build work itself; it is the only thing in the run that talks to you. Each agent gets a narrow job and writes into the run's scratch dir. Open a card for its model and what it writes.

sonnet requirements step 1, and the two pre-Spec gates

Four modes: questions writes your clarifying questions, write turns your answers into requirements, research-update folds in the research and surfaces the genuine decisions, finalize writes the approval summary. Analysis, not design.

Writes: requirements-questions.md, requirements.md, research-questions.md, requirements-human.md.

sonnet research step 2

Grounds the requirements in the real codebase (and a budgeted web search only when an off-the-shelf solution is plausible), verifies claimed dependencies, and tags each claim verified, cited, or assumed.

Writes: research.md.

opus spec step 3

Synthesizes requirements and research into a spec a coder can build from with zero planning context, each acceptance criterion marked core or deferred, Open Questions at the top for the gate.

Writes: spec.md.

opus code step 4, and every fixer pass

In build mode, implements the spec's core criteria and writes end-to-end tests from the spec's words. In fixer mode, runs after each reviewer and after certification, fixing that pass's findings one at a time by severity and marking each outcome.

Writes: the repo (code and tests), code-notes.md; marks outcomes in review.md.

opus review-correctness first reviewer, and certification

Bugs and edge cases, hook and lifecycle timing, i18n, spec compliance (no stubs), reuse and right-sizing, acceptance-criteria completeness, and test quality. Report-only.

Writes: [CO-N] / [CO-R] findings in review.md.

sonnet review-design second reviewer

CSS and design-token reuse, cascade discipline, block control hierarchy and UI states, template semantics and accessibility. Report-only.

Writes: [DES-N] findings in review.md.

opus review-performance third reviewer

N+1 and unbounded queries, caching and invalidation, autoloaded-option bloat, heavy every-request hooks, and a short frontend Core Web Vitals pass. Report-only.

Writes: [PERF-N] findings in review.md.

opus review-security fourth reviewer, and certification

Nonce versus authorization mix-ups, injection, context-correct escaping, secret storage, SSRF, and upload handling. Defaults to skeptical. Report-only.

Writes: [SE-N] / [SE-R] findings in review.md.

sonnet demo-recording closeout

Records a short WordPress Playground walk-through of the feature. Backend-only work with no UI is skipped, not filmed blank. Never gates closeout.

Writes: demo-recording.md, and demo.webm when it records.

opus advisor closeout

Reads the finished component through the shared advisory perspectives and offers non-blocking observations. It files no findings and drops anything the reviewers already caught. Finding nothing is normal.

Writes: advice.md.

opus compound-learning closeout

Proposes durable, paste-ready lessons for this plugin's own CLAUDE.md from the run's findings and summary. It proposes only, and never edits your CLAUDE.md.

Writes: compound-learning.md.

opus feedback-loop opt-in, a later session

Looks back at one finished run and proposes edits to your own local agent files. Pure-proposal; never runs during a build. See the Feedback Loop tab.

Writes: feedback-loop.md.

Checks: what a change passes before it becomes a PR

The review loop is interleaved: one reviewer, then a Code fixer pass, then the next reviewer, so every reviewer sees code the previous fixes already changed. There is no cross-reviewer duplicate to reconcile, and no merge or dedup step. Before each reviewer the orchestrator recomputes the changed-file surface fresh from the working tree.

ReviewerLooks for
CorrectnessBugs and edge cases, hook and lifecycle timing, i18n, spec compliance, reuse and right-sizing, acceptance-criteria completeness, test quality.

The fixer, bound by severity

The Code fixer takes one reviewer's findings at a time, Critical before High before Medium before Low, and the outcome it may use is bound to the severity:

SeverityAllowed outcomes
Critical / HighFIXED or BLOCKED only, never deferred
MediumFIXED or DEFERRED-PENDING-ACCEPTANCE
LowFIXED or DEFERRED, with a reason

Certification then re-runs correctness and security over the fix delta once, with no loop, and fixes both sets in one batch. A BLOCKED Critical or High is a release blocker.

The release gate

Derived on the spot at closeout, with no stored verdict. It passes only when both hold: every required check passed (syntax, the project's tests, the build, and the end-to-end suite, where a suite that collects zero tests counts as a fail), and no Critical or High is left BLOCKED in review.md. On pass, the orchestrator prints the push and PR commands; on fail it prints none and names each failing check and blocking finding. The gate is skipped when there is no git repo.

Everything is files in the run directory

A run keeps nothing important in its head. Every artifact lives under one scratch dir on the branch, and state.json is the resume authority: the orchestrator is its only writer, it advances only after a step returns STATUS: ok, and it is bootstrapped from which artifacts exist when it is absent. A human badge marks a file you read or sign off on.

What state.json holds

FieldWhat it records
phaseThe resume bucket: requirements, requirements-gate, research, research-gate, spec, gate, code, review, certify, closeout, done.
components[]The plugins, themes, and mu-plugins found in Preflight, with how to activate each. The end-to-end harness mounts these.
reviews_passed[]A reviewer's name once its review and fix pass are done; certification appends certify.
approvals.gatefalse until the spec is approved, then true. The two pre-Spec gates are tracked by phase alone.
start_branchThe branch the run started on, the fork point the review surface and fix delta diff against; null without git.

On a re-invocation, Preflight reads state.json and resumes from the recorded phase, never overwriting an artifact you may have edited or re-running a completed step. The run-id (which names the scratch dir) is derived from the task text, falling back to the branch name, then to run-YYYYMMDD-HHMM. Nothing else is tracked: no SHAs, no release-verdict object, no per-artifact hashes.

The Feedback Loop

The one place the pipeline's own agents get improved. It is opt-in and runs in a later session, never as part of the build or closeout.

/principal-wp-starter-pipeline feedback-loop <run-id> [pr]

Run on a finished task, usually after its PR is merged, it looks back at that one run for evidence that an upstream agent should have done better and proposes edits to your own local principal-wp-starter-pipeline-* agent files. It only proposes. It writes feedback-loop.md with diffs and ready-to-paste log rows, and you apply the ones you agree with by hand.

It reads the gate diff (spec.gate.md against the spec you approved), the run artifacts (review.md, summary.md, code-notes.md, advice.md), this task's sub-agent transcripts, and, with your go-ahead, the PR comments (read-only, treated as untrusted evidence). It may edit only the four build agents, the demo-recording step, the four reviewers, and the Advisor, and never the Feedback Loop itself, Compound Learning, the orchestrator, or setup. Each proposed edit carries a one-line consequence check, and applying it changes the pipeline for every project.
