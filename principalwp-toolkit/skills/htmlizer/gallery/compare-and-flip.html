Notification preferences redesign — pick a layout

Two ways to reorganize the notification settings page. Flip between side by side and one at a time to compare them, then say which one should ship.

Recommended: Option B — grouped by event type (why)Support has logged several tickets where a customer thought they'd turned off all security alerts by unchecking just one channel. Option B puts every channel for an event in one place, so that mistake is harder to make.

Option A — Grouped by channel

Email
SMS
Push notifications

What differs

+ Matches the grouping already used on the Team Settings page — familiar to anyone who's changed a setting there before.

+ The API response shape is flat, one object per channel — the existing mobile app already reads this shape, so shipping this needs no mobile client changes.

− Turning off "order shipped" emails means scanning three separate channel sections to find every place email touches an order update.

− Security alerts can be muted per channel without the other channels being visible at the same time — support has flagged tickets where a customer thought unchecking Email under Security also silenced SMS.

API response shape — GET /account/notification-preferences
{
  "email": { "enabled": true, "order_updates": true, "promotions": false, "security_alerts": true },
  "sms": { "enabled": false, "order_updates": false, "promotions": false, "security_alerts": true },
  "push": { "enabled": true, "order_updates": true, "promotions": true, "security_alerts": true }
}

Option B — Grouped by event type

Order updates
Promotions & offers
Security alerts

What differs

+ Security alerts render as one section with every channel visible together — a customer can't half-disable them without seeing what's still on.

+ Each event type reads as a single decision ("how do I want to hear about order updates?") instead of three separate channel decisions.

− The API response shape nests by event first, then channel — the opposite of what the mobile app currently parses, so mobile needs a rewrite before this can ship there.

− Without a mobile rewrite, this would need to launch web-only first, which splits the settings experience across platforms for a while.

API response shape — GET /account/notification-preferences
{
  "order_updates": { "email": true, "sms": false, "push": true },
  "promotions": { "email": false, "sms": false, "push": true },
  "security_alerts": { "email": true, "sms": true, "push": true }
}
