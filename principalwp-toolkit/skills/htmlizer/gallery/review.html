A retried submit can no longer buy the cart twice

Today POST /checkout/orders writes an order for every request that reaches it, so a double-click, a mobile network retry or the client's own auto-retry each buy the cart again. NW-420 puts a claim in front of the handler: the request carries an Idempotency-Key, a unique index picks exactly one caller to run the write, and everyone else is handed that caller's answer.

A double-click used to cost the customer twice. The endpoint wrote an order for every request that reached it, and the client could not tell a lost response from a failed submit — so it retried, and got a second order and a second capture. This change makes the second write unreachable.

One insert decides who writes

The whole scheme is a single statement. A request carrying an Idempotency-Key inserts a row into idempotency_keys with ON CONFLICT (key, endpoint) DO NOTHING, and the unique index picks the winner: a rowCount of 1 means this caller runs the handler, 0 means somebody else already is. Nothing reads the table first, on purpose — a read-then-write leaves a window that two simultaneous submits both walk straight through, and two simultaneous submits is precisely the case being defended against.

The loser is not made to queue. It reads the row that beat it and answers from what it finds: the stored response when the first request has finished, 409 request_in_flight with a Retry-After when it has not, 422 idempotency_key_reused when the fingerprint says this is a different request wearing the same key.

What the fingerprint is for

A key on its own would let a client reuse one key across two different carts and be handed the first cart's order both times. So the row also carries a SHA-256 of the canonical body — keys sorted, whitespace dropped — over the session id, the line items and the payment method id. Canonical rather than raw, because the web client and the mobile client serialise the same submit differently and both have to hash the same.

The fields left out of that hash are a deliberate and arguable choice. Shipping address and promo code are outside it, so a submit that changes only those hashes identically to the first one and is answered with the first one's order. Which fields belong in the fingerprint is one of the open questions.

What happens when the handler fails

createOrder throwing is not a duplicate — nothing was written — so the key row is deleted and the original error goes back untouched. The customer's next attempt claims the key fresh and runs for real, which is the behaviour anyone would expect from a failed checkout.

That release only runs while the process is alive to run it. A pod killed between the claim and the response leaves its row in_flight, and the only thing that clears it is the 24-hour sweep; until then every retry from that customer gets a 409. NW-421 adds a short lease so a stale in_flight row can be re-claimed. Whether that lease has to land before enforcement is turned on is the review's one condition on this change.
