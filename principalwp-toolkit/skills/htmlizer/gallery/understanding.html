How a paid order becomes a shipment

Northwind's fulfilment pipeline picks up a checkout session the moment payment is captured and walks it through seventeen stages grouped into four tracks — intake, reserve, settle, dispatch. Two of those stages need a signature and park the job for a human: a held order's manual review, and the lead sign-off before dispatch. Three ways in below: the lane table that decides how much handling an order earns, the worker functions that drive a job stage to stage, and the four records one job leaves behind.

How much handling does an order earn?

Stage IN·4 reads one cell out of a three-by-three table: order value picks the row, the number of raised risk signals picks the column, and the cell names the lane. There is no score and no tie-break. Two handling flags sit outside the table entirely — they switch extra stages on rather than changing the lane. The 24-hour clock

Every lane that is actually moving inherits the same promise: the parcel is in a carrier's hands within 24 hours of payment capture. The fulfilment worker, function by function

A captured checkout session lands on the queue and the worker takes it from there: build the job, raise the signals, read the lane, hold the stock, then advance one stage at a time until the carrier has it — with a dedupe wrapper around the whole thing because the payment provider will deliver the same webhook twice. Six functions, six files, all in northwind/storefront at 9c4e1a7. Open each section to read the code with a plain-language note. Sections open and close independently.

One job, four records

A single fulfilment job writes itself down four times, and each record answers a different question. Config says which warehouses and notifiers exist at all. Lane rules is the table, owned by the pricing service rather than by fulfilment. Job record is the append-only document the worker replays to find out where it is. Customer view is the short, filtered list the storefront is allowed to show.

Read once when the worker boots, never re-read mid-job. warehouses bounds where a reservation is allowed to land; coldChain is a subset, so a cold-chain basket that cannot be served from sea-1 fails the reserve track rather than silently shipping warm. notifiers.disabled drops outbound messages without touching the stage list — the six below are off in staging, so a job that reaches DP·4 there sends nothing to anybody.

The table lives in the pricing service, not in fulfilment — pricing already owns value bands for tax and discounting, so putting the lane table anywhere else would mean two definitions of "high value" drifting apart. Fulfilment calls it once at IN·4 and stores the answer. Excerpt from src/pricing/rules.py lines 88–121.

src/pricing/rules.py · assign_lane
# Row = order value band. Column = how many risk signals were raised,
# capped at 2. Nine cells, four lane names. No score, no tie-break.
VALUE_BANDS = ((0, 400, "low"), (400, 1200, "mid"), (1200, None, "high"))

LANE_TABLE = {
    #          0 signals      1 signal      2+ signals
    "low":  ("express",    "standard",   "held"),
    "mid":  ("standard",   "standard",   "held"),
    "high": ("insured",    "insured",    "held"),
}


def value_band(total_cents: int) -> str:
    dollars = total_cents / 100
    for low, high, name in VALUE_BANDS:
        if dollars >= low and (high is None or dollars < high):
            return name
    raise ValueError(f"no band for {total_cents}")


def assign_lane(total_cents: int, signals: list[str]) -> str:
    # NW-531: a basket with any signal at all must never reach "express",
    # which is why the low row moves to "standard" at one signal.
    return LANE_TABLE[value_band(total_cents)][min(len(signals), 2)]

Three of the seventeen stages are customer-facing. Everything else — warehouse choice, signal names, the failed capture attempt above — stays internal, and the filter is an allow-list rather than a deny-list so a new stage is invisible until somebody deliberately adds it. Excerpt from src/checkout/timeline.ts lines 27–54.

src/checkout/timeline.ts · timeline
// Allow-list, deliberately. A stage added in NW-530 stayed invisible to
// customers until it was named here, which is the behaviour we want.
const CUSTOMER_VISIBLE: Record<string, string> = {
  "ST.1": "Payment confirmed",
  "DP.2": "Packed and ready",
  "DP.4": "Handed to the carrier",
};

export function timeline(job: Job): TimelineEntry[] {
  const seen = new Set<string>();
  return job.events
    .filter((e) => e.result === "ok" && e.stage in CUSTOMER_VISIBLE)
    .filter((e) => (seen.has(e.stage) ? false : seen.add(e.stage)))
    .map((e) => ({ at: e.at, label: CUSTOMER_VISIBLE[e.stage] }));
}
Rule — read this

Append, never overwrite. No stage outcome is ever edited or deleted, including failures — the retried ST·1 above sits next to the attempt that timed out, not on top of it. Position in the pipeline is derived by replaying events against the lane's stage set, so a worker that dies mid-stage costs one replay and nothing else. A job ends in exactly one of three terminal states: ✓ shipped / partially_shipped / ✗ cancelled.
